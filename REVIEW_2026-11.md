# Orthotect — Comprehensive Code Review & Development Roadmap

**Repository:** `seotarek/orthotect` @ `v1.8.8` (branch `main`, commit `c2ba2de`)
**Review date:** 2026-11-20
**Scope:** All six deterministic gates, the CLI, the configuration engine, the test suite, and release/docs consistency.
**Method:** Static reading of every gate implementation, then empirical proof of each defect via a targeted failing fixture, then a fix, then a regression test. Nothing in this report is asserted without a command that demonstrates it.

---

## 1. Executive Summary

Orthotect's central claim is that its gates are *deterministic* and *fail-closed*: if a rule is violated, the build must exit `1`. That claim was true for the rules the gates checked, but it was **not** true of the gates themselves. Five independent fail-open paths were found in which non-compliant code could pass with a green build, plus three configuration keys that were documented, parsed, and then silently ignored.

All findings below have been fixed in-place and locked with regression tests. The suite grew from 361 to **415 tests** (54 new regression tests, verified against the `HEAD` baseline), and the full suite plus both reference targets (`docs/`, `examples/golden-showcase`) now pass.

The most serious defect was in the flagship feature: the BiDi gate — the one that distinguishes Orthotect from generic linters — accepted `margin-left: 8px !important` and every four-value physical shorthand. That is a **direct bypass of the product's core value proposition**, and it was reachable by any AI agent that appended `!important` to silence a warning.

## 2. Critical Findings

### C1 — BiDi gate accepted `!important` and physical shorthands

**Where:** `gates/gate_bidi_logical.py`

**Why it matters:** The BiDi gate exists to guarantee that a layout mirrors correctly between LTR and RTL. Physical properties (`margin-left`) do not mirror. A rule that can be defeated by a suffix is not a gate; it is a suggestion.

Two separate holes, both in the zero-dependency fallback scanner (`scan_css_content_fallback`) that runs whenever `tinycss2` is unavailable — which is the *default* install, since `tinycss2` is optional:

1. `margin-left: 8px !important` did not match the value comparison, because the parsed value was `8px !important` rather than `8px`, so the declaration was treated as allowed.
2. `margin: 0 8px 0 24px` (asymmetric four-value shorthand) had no branch at all. The shorthand sets `margin-left: 24px` and `margin-right: 8px` — both physical — yet the gate said nothing.

Critically, the `tinycss2` path *did* handle `!important`, so the two code paths disagreed. Whichever dependency happened to be installed changed the verdict. That is the opposite of determinism.

**Fix:** A single shared evaluator, `evaluate_declaration()`, now serves both paths, so the `tinycss2` and fallback scanners cannot drift again. It normalises `!important` away, and adds an explicit shorthand branch that flags any four-value shorthand whose inline pair is asymmetric, with a copy-pasteable logical replacement:

```
Logical separation: margin-block: 0 0; margin-inline: 24px 8px;
```

Symmetric shorthands (`margin: 0 8px`) remain valid, since they are direction-neutral.

**Regression tests:** `test_fallback_enforces_4_value_shorthand`, `test_important_flag_cannot_bypass_directional_check`, `test_symmetric_shorthand_still_accepted_in_fallback`.

### C2 — The security gate trusted any path containing `/tests/`

**Where:** `gates/gate_security_audit.py`, `is_safe_context()`

**Why it matters:** `is_safe_context()` returned `True` for any filepath matching `/tests/`. The original intent was to let the project's own test suite assert on XSS payloads without self-flagging. The effect was much wider: application code that merely *lives* under a test-shaped path — `src/tests/e2e_driver.js`, `app/test/mock_server.js`, fixture servers, e2e helpers — was silently excluded from the security audit. Since e2e drivers routinely interpolate user input into `innerHTML` and `eval`, this is precisely the code most likely to contain a real DOM XSS.

Worse, the exemption was invisible: the JSON report listed `tests/` under "excluded" as though it were a deliberate, scoped policy, so a reviewer reading the report would believe the scope was intentional.

**Fix:** Path trust is now narrow and explicit. Only two path classes are exempt: the scanner's own source file, and the curated `knowledge/` and `references/` corpora. Comment-only matches are still exempt by content, not by path. Directory-level exclusion of `tests`/`test` now applies **only at the scan root**, which preserves the legitimate use case while keeping nested application code auditable. The report's `scope.excluded` string was rewritten to say exactly that.

**Regression tests:** `test_tests_path_is_not_trusted_by_is_safe_context`, `test_nested_tests_directory_is_audited`, `test_root_level_tests_directory_is_still_excluded`, `test_config_exclude_is_honored`, `test_excluded_path_outside_config_is_still_audited`.

## 3. High Findings

### C3 — Flag-before-path resolved the wrong audit target

**Where:** `bin/orthotect.js`, `gates/run_all_gates.py`, `gates/gate_security_audit.py`, `gate_contrast_wcag.py`, `gate_fsm_integrity.py`, `gate_no_slop.py`, `gate_cwv_budget.mjs`

**Why it matters:** This is the single most dangerous class of bug in a verification tool, because it produces a *green build on the wrong code*. Every documented invocation form works (`orthotect verify ./src --json`), which is exactly why nobody noticed the broken form.

The CLI stripped flags with `args.filter(a => !a.startsWith('--'))`. For `orthotect security --json ./src`, the positional list became `['security', 'json', './src']`, so the target resolved to the literal string `json` — a non-existent path — while `--format json` was *also* detected by a separate substring test on the whole argv. The gate then either exited `1` with a confusing "does not exist" message, or (when run from a directory that happened to contain `json`) scanned the wrong tree and exited `0`.

The standalone gates had the same bug in miniature: `sys.argv[1]` blindly became the target, so `gate_contrast_wcag.py --json ./src` reported:

```
❌ [REJECT] Missing required Design Token files in target: --json
```

**Fix:** A single `parsePositionals()` in the CLI understands value-taking flags (`--format`, `--out`, `--output`, `--config`, `-o`), `--flag=value` forms, and `--` terminators. A separate `resolveOutputFormat()` decouples format detection from path detection. The same logic was mirrored into the orchestrator (`positional_arguments`, `parse_requested_format`) and into each standalone gate. The legacy bare-token form (`run_all_gates.py <dir> json`) still works, so existing scripts do not break.

**Regression tests:** `TestCLIArgumentResolution` (5 tests: flag before path, flag after path, `--format json`, `--format=json`, `verify` path passthrough) and `TestGateStandaloneFlagParsing` (4 tests, one per standalone gate).

---

### C4 — Comment masking was not string-aware

**Where:** `gates/gate_no_slop.py`, `mask_comments()`

**Why it matters:** The fix for comment false positives introduced a worse bug. The masker scanned for `//` anywhere in the text, so the `//` in `"https://cdn.example.com"` was treated as a comment opener and everything after it on that line was replaced with spaces. Real slop sharing a line with a URL — `data-src="https://x.io"` next to an emoji button, or a CSS rule following a `url("https://…")` — passed the gate completely undetected.

This is a textbook fail-open: the gate's own bookkeeping (comment tracking) disabled the gate's enforcement.

**Fix:** The masker is now a small state machine with string awareness. It tracks `"`, `'`, and `` ` `` quoting, honours backslash escapes, and only treats `//`, `/*`, and `<!--` as comment openers in normal state. String *contents* are deliberately left unmasked so that genuine slop inside template strings is still caught. Unterminated single-line strings recover to normal state instead of swallowing the rest of the file.

**Regression tests:** `test_anti_pattern_after_url_in_string_still_fails`, `test_css_slop_after_url_in_string_still_fails`, `test_comment_marker_inside_url_does_not_mask_later_lines`.

### C5 — `cwv.maxDomNodes` was never enforced

**Where:** `gates/gate_cwv_budget.mjs`

**Why it matters:** `core/config.py` defines `maxDomNodes: 1500` in `DEFAULT_CONFIG`, `get_cwv_config()` returns it, and the README documents it. The gate read `maxDomDepth` and ignored `maxDomNodes` entirely. A page with 5,000 flat sibling nodes — a real performance problem, and the classic symptom of an agent rendering an unbounded list — passed cleanly, because depth stayed at 3.

The node count was also computed by a second, redundant AST walk. `calculateMaxDomDepth` and the depth check each traversed the tree separately.

**Fix:** A single exported `analyzeDomStructure(html, filePath)` returns `{ maxDepth, elementCount }` from one iterative AST pass, and `calculateMaxDomDepth` delegates to it. Both budgets are now enforced against `orthotect.config.json`, with `maxDomNodes: 0` as the documented opt-out. The traversal also keeps its pre-existing 200,000-node adversarial guard.

**Regression tests:** `TestCWVNodeBudget` — flat DOM over budget fails, within budget passes, the 1,500 default binds, and `0` disables.

## 4. Medium Findings — Configuration That Did Nothing

Three keys in `orthotect.config.json` were parsed, deep-merged, returned by a getter, documented in the README, and then never read by the gate they belonged to. A user who set them got a silent no-op — the worst outcome for a configuration surface, because it teaches the user that the tool ignores them.

**C6 — `contrast.level`.** The gate hardcoded AA. A project declaring `"level": "AAA"` received a PASS at AA quality, i.e. a false certification of the stricter standard. Fixed by loading config in `main()` and computing `required_req` per pair. The gate now also warns on an unrecognised level rather than silently defaulting.

**C7 — `bidi.allowCamelCase`.** The gate had no camelCase escape hatch at all in its main path, so React Native and JSX projects — where camelCase is the *only* legal syntax and CSS logical properties do not exist — had no way to pass except by disabling the gate. Fixed by threading `allow_camel_case` from config through `scan_file` → `scan_js_content` → `scan_js_style_block`. It relaxes the JSX property check **only**; physical CSS still fails, which the tests pin explicitly.

**C8 — `exclude`.** Honoured by BiDi and Contrast, ignored by Anti-Slop and Security. A user who excluded a generated bundle directory still got blocked by it. Fixed by wiring `load_orthotect_config` + `is_path_excluded` into both gates, applied to directories and files.

**Regression tests:** `test_allow_camel_case_config_disables_jsx_property_check`, `test_camel_case_still_rejected_without_config`, `test_allow_camel_case_does_not_weaken_css_enforcement`, `test_config_exclude_is_honored` (×2).

## 5. Low Findings — Honesty and Consistency

**C9 — `--fix` scope.** `run_all_gates.py --fix` forwarded `--fix` to the BiDi gate only, but printed nothing about that. Users reasonably assumed all six gates self-heal. The orchestrator now states the scope before running.

**C10 — Missing `parse5`.** The gate crashed with an unhandled module-resolution error. It now fails closed with an actionable message naming the exact install command, and distinguishes "dependency missing" from "HTML malformed".

**C11 — Documentation drift.** `ARCHITECTURAL_SUPERIORITY.md` claimed 355 tests in one place and 361 in another; `CLAUDE.md` said "5 deterministic quality gates" while the code runs 6; `README.md`, `CLAUDE.md`, and `ci.yml` all hardcoded 361. All were reconciled to the actual collected count (now 415), and the "100% Pure Python & Node Standard Libraries" claim was corrected to reflect that the DOM gate requires `parse5` — the one honest caveat in an otherwise dependency-free tool. The README's config example also advertised a `contrast.strictMode` key that has never existed in `DEFAULT_CONFIG`; it was removed rather than implemented, since `level` already covers the use case.

### Note on skipped tests

An earlier revision of this review recorded 99 skipped tests. Those skips were **not** an inherent limitation of the environment — they were caused by `node_modules` never having been installed, so `playwright-core` and `parse5` were missing while a Chrome binary was in fact present. Installing the declared dependencies (`npm install`, 3 packages) made every previously-skipped test execute: the suite now reports **415 tests, OK, 0 skipped**, including all 33 browser tests and all `parse5`-dependent DOM tests.

This distinction matters for the tool itself: the skip guards fire on a missing *dependency*, and a present Chrome with a missing `playwright-core` produced a hard `ERR_MODULE_NOT_FOUND` failure rather than a skip. That is the correct fail-closed direction for CI, but it means the browser tests' dependency precondition (`playwright-core`) is not checked the same way the binary is. See `P0-3` for the planned fix.

Both classes still **fail** when `CI=true` and skip locally, so a CI run cannot silently lose coverage. That behaviour is itself tested.

## 7. What Is Genuinely Good

The review should not read as uniformly negative; several design decisions here are better than typical for a tool of this kind.

The **security gate's taint analysis** is real work, not regex theatre. It tracks sanitizer provenance through imports, aliases, destructuring, and parameter shadowing, and it correctly *rejects* a commented-out import as a source of trust (`test_indirect_dom_xss_commented_import_disqualified`). The CHANGELOG entries for 1.8.6–1.8.7 show a genuine adversarial loop — each bypass was found and closed with a negative test.

The **DOM gate's CSS cascade handling** respects specificity and source order rather than pattern-matching `aspect-ratio` anywhere in a file, and it validates `calc()` against the actual W3C grammar (whitespace around `+`/`-`, type compatibility, scientific notation). That is well beyond what a linter normally attempts.

The **parallel orchestrator** is a genuine 6× speedup and stays under 600 ms on both reference targets, which matters because a gate that costs seconds gets disabled.

The **`--fix` engine** masks comments and string literals before rewriting, so it does not corrupt prose. That is the right instinct.

## 8. Prioritised Development Roadmap

Ordered by value per unit of risk. Each item is scoped to be independently shippable.

### P0 — Restore trust in the verdict (do first)

1. ✅ **Publish a `--strict` exit-code contract.** *(shipped — see §9)* Today a gate that cannot run (missing `parse5`, unreadable token file, unparsable config) fails closed at exit `1`, but it fails with the *same* code as a genuine violation. CI cannot distinguish "your code is bad" from "the tool is broken". Introduce exit `2` for tool/configuration errors and document it. This is the single highest-value change remaining: it is what separates a checker from a certifier.

2. ✅ **Ship `parse5` as a real vendored artifact or drop it.** *(shipped — see §9)* Resolved by keeping `parse5` as the single declared runtime dependency and fixing the two genuine defects found on audit: the remediation message sent users to a directory where the install can never take effect (the import resolves from the gate file), and a missing parser crashed as exit `1` instead of exiting `2`. "Drop it" was rejected on evidence — the media/cascade analysis needs a real HTML5 tree, not a tokenizer — and vendoring was rejected as 448 KB of committed third-party code (parse5 + its transitive `entities`) buying only the bare-checkout case. The README now states the precondition honestly.

3. ✅ **Add a self-audit gate.** *(shipped — see §9)* `npm run audit:self` runs all six gates against the repository root and is a required CI step. It is proven non-vacuous: an injected physical CSS declaration makes it exit `1` and name the file.

### P1 — Close the remaining fail-open surface

4. ✅ **Make the BiDi gate `--fix`-verify in the same pass.** *(shipped — see §9)* `apply_bidi_fixes_to_file()` now returns the post-fix scan, and `main()` asserts it is empty: a partial repair prints `[PARTIAL FIX]` with the exact remainder and still exits `1`. Auditing this path also surfaced the JSX/CSS rule-parity gap and an invalid border-family suggestion; both are fixed and pinned.

5. ✅ **Extend the shorthand rule to `border-width`/`border-style`/`border-color` asymmetry.** *(shipped — see §9)* Fixtures now cover the border family in CSS, HTML `<style>`, inline `style=""`, JSX and `StyleSheet.create()`. Writing them exposed that the **repair** path had no shorthand branch at all for CSS, no end-of-input terminator for inline style attributes, no call from the `StyleSheet.create()` branch, and dropped `!important` on expansion — all four fixed and pinned. A 24-construct parity probe now reports zero detected-but-unrepaired cases.

6. ✅ **Give the security gate a baseline/allowlist file.** *(shipped — see §9)* `core/security_baseline.py` reads a committed `orthotect-security-baseline.json` keyed on file + rule + line with a mandatory justification. Globs are rejected, suppressions are shown in all three output formats, an unreadable baseline exits `2`, and a stale entry is reported without failing. Testing it surfaced two path-resolution defects (single-file targets, monorepo parent baselines), both fixed and pinned.

### P2 — Developer experience

7. ✅ **Unify argument parsing into one module.** *(shipped — see §9)* Extract it to `core/cli_args.py` and `core/cli_args.mjs` before a fifth copy appears.

8. ✅ **Add `orthotect explain <rule-id>`.** *(shipped — see §9)* All 42 rules carry `citation`, `summary` and `fix`; `orthotect explain` and the gates read the same registry, so a violation's id and its spec citation cannot drift apart. This converts the gate from a wall of failures into a teaching tool, which is the stated product thesis.

9. ✅ **Emit SARIF.** *(shipped — see §9)* `--format sarif` puts all six gates into GitHub Code Scanning as one run with a unioned rule catalogue. The mapping did turn out to be nearly mechanical — with one correction: the rule id has to be carried from the detection site rather than re-derived from message text, or the SARIF layer becomes a second copy of the detection logic.

### P3 — Architecture

10. ✅ **Split `gate_security_audit.py` and `gate_bidi_logical.py`.** *(shipped — see §9)* Both are now packages, `gates/_security/` and `gates/_bidi/`, with one module per rule family and an acyclic dependency graph. The entry points keep their original paths, and the refactor was verified byte-identical across 21 target×format cases rather than assumed equivalent.

11. ✅ **Version the rule set, not just the package.** *(shipped — see §9)* `rulesVersion` is now a semver string independent of the package version, paired with a `rulesDigest` over the rule identities so a consumer can verify two reports used the same rules rather than trusting a hand-bumped number.

12. ✅ **Property-based testing for the parsers.** *(shipped — see §9)* 23 generated-input tests cover the CSS shorthand splitter, the `calc()` validator and the comment masker, each property paired with a rejection mirror. A hand-rolled seeded generator keeps the suite dependency-free.

## 9. Roadmap Progress

### P0-1 — Exit-code contract (shipped 2026-11-20)

Delivered: `core/exit_codes.py` and `core/exit_codes.mjs` define the three codes once per language; all five Python gates, the Node DOM gate, the orchestrator, `bin/orthotect.js`, the token compiler, the context optimizer, the knowledge-base CLI, and the release-sync script now emit them instead of bare integers.

The aggregation rule is the part that actually matters in CI: `TOOL_ERROR` outranks `VIOLATION`, so a run in which one gate could not start never certifies a target on the strength of the other five. Any unrecognised child status (a crashed gate, a signal kill, a failed spawn) is also mapped to `2`, because a gate that never completed makes no claim about the code.

Evidence:

| Scenario | Command | Exit |
| :--- | :--- | :---: |
| Genuine breach | `gate_no_slop.py <dir with inline hex style>` | `1` |
| Path typo | `gate_no_slop.py /nope/nothing` | `2` |
| Missing token architecture | `gate_contrast_wcag.py <empty dir>` | `2` |
| Missing FSM specs | `gate_fsm_integrity.py <empty dir>` | `2` |
| Missing `parse5` | `gate_cwv_budget.mjs <any dir>` | `2` |
| Orchestrator, bad target | `run_all_gates.py /nope/nothing` | `2` |
| Orchestrator, breach + missing `parse5` | `run_all_gates.py <dir with slop>` | `2` (not 1) |
| CLI, bad target | `bin/orthotect.js verify /nope` | `2` (was `1`) |
| Reference target, all deps present | `run_all_gates.py examples/golden-showcase` | `0` |

`tests/test_exit_codes.py` (22 tests) pins the boundary from both directions, including a source-level guard that fails if anyone reintroduces a bare `sys.exit(1)` into a gate. The contract is documented in the README with a `case $?` CI recipe and the `exitCode` field of the `--json` report.

### P0-2 — `parse5` dependency honesty (shipped 2026-11-20)

The dependency itself was kept; the two defects around it were fixed. Auditing the gate's failure
path — rather than only its success path — surfaced both:

- **The remediation message could never work.** It instructed the user to install `parse5` *"in the
  project being verified"*. Node resolves that import relative to the gate file, so the advice is
  inert. The message now names the real cause, states outright that the intuitive fix will not
  help, and gives the one command that does (`npm install` inside the Orthotect package).
- **A missing parser was reported as exit `1`.** Exported helpers dereferenced `null`
  (`TypeError: Cannot read properties of null (reading 'parse')`), which Node surfaces as exit 1 —
  a tool error dressed as a code violation, exactly inverting P0-1. All analysis now funnels
  through `requireParse5()`, which throws the typed `ParserUnavailableError`; the CLI translates
  it to exit `2`.

`tests/test_cwv.py::TestMissingParserContract` (3 tests) pins both, including an assertion that the
message does **not** contain the old, misleading instruction.

### P0-3 — Self-audit (shipped 2026-11-20)

`npm run audit:self` runs all six gates against the repository root and is a required CI step,
enforced by a test that fails if the step is removed. The scope decision is deliberate: auditing
`gates/` in isolation legitimately exits `2`, because the token, FSM and DOM gates resolve their
inputs relative to the audit root — so the root is the only target that evaluates the project the
way a user's project is evaluated.

It is proven non-vacuous rather than merely present: appending `margin-left: 16px` to
`core/config.mjs` makes the self-audit exit `1`, fail the BiDi and DOM gates, and name the file.
Removing the probe returns it to exit `0`.

### P1-1 — `--fix` verifies its own result (shipped 2026-11-20)

`apply_bidi_fixes_to_file()` previously subtracted the remaining violation count from the initial
count and printed the difference as "repaired", then classified the file purely on the re-scan. A
file holding both a repairable and an unrepairable violation therefore produced output that read
like a successful repair, with nothing saying the file still failed. The function now returns the
post-fix scan and `main()` asserts it is empty; a partial fix prints `[PARTIAL FIX]` with the exact
remainder and still exits `1`.

Implementing that assertion exposed three further defects, all now fixed:

- **JSX style objects skipped whole rule families.** Asymmetric four-value shorthands and the
  value keywords `float`/`clear` were rejected in plain CSS but accepted in `style={{ … }}` and
  `StyleSheet.create({…})` — *the C1 bypass, re-opened in a second syntax*. Six declaration forms
  were empirically confirmed passing in JSX while failing in CSS. The JSX block now delegates to
  `evaluate_declaration()`, the single evaluator the CSS paths already share, so the two syntaxes
  cannot drift again.
- **The border-family suggestion was not valid CSS.** `border-width` produced the suggestion
  `border-width-block`, which is not a property. `logical_shorthand_pair()` now inflects the border
  family as `border-block-width` (the infix precedes the sub-property) and everything else as
  `margin-block` / `scroll-margin-block`.
- **`apply_bidi_fixes_to_file()` ignored `allow_camel_case`,** so it verified against rules the
  run was not enforcing. The configuration is now threaded through both scans.

`tests/test_bidi_fix_verify.py` (16 tests) pins the partial-fix contract, JSX/CSS rule parity in
both directions, auto-fix reaching green for the newly-detected forms, and the shorthand
inflection table.

### P1-3 — Security baseline / allowlist (shipped 2026-11-20)

Removing the blanket `/tests/` exemption (C2) was correct, but it left a usability hole: a
legitimate fixture — a test asserting on an XSS payload, a deliberately vulnerable example —
blocks the build, and the only escape was to re-widen path trust, which is exactly the fail-open
C2 closed.

`core/security_baseline.py` adds a committed `orthotect-security-baseline.json` that suppresses
**one file + one rule + one line**, each requiring a `justification`. Globs, absolute paths and
missing justifications are rejected with `exit 2`, so a suppression can never silently widen into
the blanket exemption it replaced. The module is loaded from the audit root (falling back to the
parent, for monorepos) and every suppression is shown in the console, `--json` and `--md` reports —
an invisible suppression is indistinguishable from a missed detection.

Two path-resolution defects were found by testing the feature rather than reading it, and both are
now fixed and pinned:

- **A single-file target never resolved its sibling baseline.** The lookup ran from the audit root,
  which for a file target is the file's own path rather than its directory.
- **A monorepo baseline above the audited package matched nothing.** Entry paths were resolved
  against the audit root instead of the directory holding the baseline file. Since the file is the
  thing that defines the path namespace, resolving against anything else makes entries
  environment-dependent — the opposite of what a committed policy should be.

Stale entries (matching nothing this run) are reported in all three formats but do **not** change
the exit code: every file was still scanned and every rule still evaluated, so calling it an
environment failure would be dishonest, and failing on unrelated line shifts would drive teams to
delete the file rather than maintain it.

`tests/test_security_baseline.py` (31 tests) pins suppression scope (no leak across files or
lines), every fail-closed path, stale reporting, machine-readable output, and both path-resolution
defects.

### P2-2 — `orthotect explain <rule-id>` (shipped 2026-11-20)

Every violation already carried a suggestion string; what it did not carry was the standard it
violates. `core/rule_registry.py` now holds all 42 rules with `title`, `gate`, `severity`,
`citation`, `summary` and `fix`, and `orthotect explain <id>` renders that entry — the W3C
candidate recommendation for a CSS Logical Properties rule, the WCAG success criterion for a
contrast rule, the OWASP CWE for a SAST rule.

The important property is that there is **one** registry. The gates import their rule ids from it,
`explain` prints from it, and the SARIF driver catalogue is built from it, so a rule cannot be
documented in one place and emitted in another. `explain --search` and `explain --json` (which
includes `rulesVersion`) make it usable from an editor or a docs generator, not just a terminal.

### P2-3 — `--format sarif` for GitHub Code Scanning (shipped 2026-11-20)

The value of SARIF is entirely in the document being valid: GitHub silently drops any result whose
`ruleId` is not declared in `driver.rules`, so a broken document renders as a clean audit. Three
properties were therefore treated as non-negotiable.

**A tool error is never an empty result set.** "No findings" and "no analysis" must not look the
same. A gate that cannot run (missing target, no files in scope, unreadable baseline) emits
`invocations[].toolExecutionNotifications` with `executionSuccessful: false` and still exits `2`.
`merge_sarif` carries every gate's notifications into the merged run, prefixed with the gate name.

**The rule id comes from the detection site.** The first implementation classified findings by
regex over their message text in the SARIF layer. The smoke test immediately produced fallback ids
like `bidi-logical.margin-left` — the signal that this approach is a second copy of detection
logic, which rots the moment a rule is split or renamed. The gates now tag each finding with its
rule id where the finding is created (`BidiViolation(rule=…)`, `SlopFinding(rule=…)`,
`ContrastPair(rule=…)`, `FsmViolation(rule=…)`), and classification is only the fallback for the
two gates whose labels are a closed table.

**Backwards compatibility was preserved by construction.** The findings are tuple or `str`
subclasses carrying extra attributes, so console printing, test substring assertions and existing
unpacking all keep working unchanged — the console report and the SARIF document come from the same
objects and cannot disagree.

Six gates fold into **one** run, because GitHub keys alerts on `ruleId` within a run; six runs
would show the same rule six times. `core/sarif.validate_sarif` checks the fields GitHub actually
rejects a document for — undeclared rule ids, absolute artifact URIs, non-positive `startLine` —
and every gate's output is validated in the test suite.

One defect was found by the tests rather than by reading: `--format sarif` resolved the target
directory only inside the non-SARIF branch, so the machine-readable path silently audited the
default `examples/` directory instead of the requested one. The banner is human output; the target
must be resolved either way.

| Evidence | Result |
| :--- | :--- |
| `run_all_gates.py <dir> --format sarif` on a multi-gate fixture | one run, 10 results, 9 registry rule ids, `validate_sarif` clean, exit 1 |
| Tool error (missing target, no files in scope) | `executionSuccessful: false` + notification, exit 2 |
| Result with an undeclared `ruleId` | rejected by the validator |
| Absolute artifact URI, `startLine: 0` | rejected by the validator |
| Explicit MEDIUM vs absent severity | preserved vs resolved from the registry |
| DOM finding line | line 5 for a blocking script on line 5 |
| FSM finding line | the state's key, not line 1 |
| `bin/orthotect.js verify --sarif` / `security --sarif` | passthrough works; `--json` unchanged |
| Full suite | **614 tests passing** |

`tests/test_sarif.py` (23 tests) covers the builder, the merger, the validator, all six gates and
the orchestrator end to end.

### P3-1 — The two monolithic gates are now packages (shipped 2026-11-21)

`gate_bidi_logical.py` (1,553 lines) and `gate_security_audit.py` (1,427 lines) are now
`gates/_bidi/` and `gates/_security/`, one module per rule family:

| Package | Modules | Dependency shape |
| :--- | :--- | :--- |
| `gates/_bidi/` | `_runtime` `_model` `_shorthand` `_css` `_js` `_fix` `_paths` `_dispatch` `gate` | data → semantics → syntax → I/O → CLI |
| `gates/_security/` | `_runtime` `_patterns` `_ast` `_taint` `_scanner` `_cli` | patterns → analysis → scan → CLI |

The entry points keep their exact paths and names, because `package.json`, `run_all_gates.py`,
`bin/orthotect.js`, the knowledge base and the test suite all reference them. A refactor whose
purpose is to make the code easier to read should not also be a breaking change.

**Equivalence was proved, not asserted.** An `ast`-driven splitter copied every unit byte-for-byte
and aborted on any non-blank source line that did not land in exactly one module (1,455 lines for
bidi, 1,362 for security, zero dropped). Both gates were then run against a passing target, a
violating fixture, `docs/` and `examples/` in console, `--json` and `--format sarif`: **21 of 21
cases byte-identical to the originals, exit codes included.**

The split introduced three defects, and all three are the kind that would have shipped silently:

**The security gate reported its own rule table as vulnerabilities.** The engine exemption was a
single filename check. Once the patterns moved into `gates/_security/_patterns.py`, the gate scanned
its own detector and exited 1 on five findings — including the comment `# subprocess.run(cmd,
shell=True)`. A fail-closed gate that cannot pass its own audit is unusable. The fix,
`is_engine_file()`, matches on path segments rather than a filename, so the entry module and the
package directory are exempt while a user file merely *named* `src/_security/helpers.py` is not.

**The facade would have swallowed a monkeypatch.** `tests/test_bidi.py` sets
`bidi_mod.HAVE_TINYCSS2 = False` to prove the fallback tokenizer enforces the same rules as
tinycss2. A plain re-export rebinds the facade's namespace while `_css` keeps reading its own copy:
the assignment becomes a no-op, the fallback is never exercised, and the test passes. The facade is
a `ModuleType` subclass that forwards the documented mutable names to `_bidi/_runtime.py`.

**The private package name was shadowable.** `import _security` accepts any module of that name
earlier on `sys.path`, so an unrelated `_security.py` would silently replace the whole gate. Both
facades pin their own directory first. The test that pins this was itself wrong on the first
attempt: it probed `python3 gates/gate_*.py`, where the interpreter already puts the script's
directory first, so it passed with *and* without the guard. It now imports `gates.gate_*` from a
foreign working directory, and was confirmed to fail when the anchor is removed.

`tests/test_gate_packages.py` (8 tests) pins the two failure modes that are otherwise silent: a
`symtable` check that every module binds the globals it reads — a `NameError` fires only on the
branch that reaches it, so a green suite is not evidence — and a check that each entry point stays
under 60 lines, so rule logic cannot creep back in one function at a time.

### P3-3 — Property-based testing for the parsers (shipped 2026-11-20)

C1 (`!important` bypassing the shorthand check) and C4 (comment masking that was not string-aware)
were the same kind of bug: every hand-written example passed, and the failure lived in an input
nobody wrote down. Example-based tests can only find bugs the author imagined.

`tests/test_property_parsers.py` generates inputs instead. There is no Hypothesis dependency — the
generators are a hand-rolled layer over `random` with a fixed seed, so the suite stays
dependency-free and every failure is reproducible. Roughly 500 generated inputs per property.

Two design rules made the difference between a test that proves something and a test that passes:

**Every acceptance property has a rejection mirror.** `calc()` accepts `length + length` *and*
rejects `length + number`; it accepts `length * number` *and* rejects `length * length` and
`length / length`. Without the mirror, a validator that returned `true` for everything would pass
the entire class.

**Properties are stated over the pipeline the gate runs, not the function in isolation.** The
`!important` property runs `normalize_declared_value` before `split_css_values`, because a spaced
`! important` is invalid CSS the normalizer discards first. Asserting on the splitter alone would
have demanded it handle input it never receives — a test that fails for the wrong reason is worse
than no test.

Writing them surfaced two defects in the tests themselves, both worth recording because both looked
like implementation bugs at first: the Node probe read `process.argv[1]` (the script path) instead
of `argv[2]`, and a generator emitted a bare `10` where a length was required, so the validator was
right to reject `10 + 0vh` and the generator was wrong. The second is exactly why the rejection
mirrors exist.

### P3-2 — Rule-set versioning (shipped 2026-11-20)

`RULES_VERSION` was an integer tied to nothing in particular. A rule that tightens changes what a
report says without changing any API, so a single version number for both the package and the rules
forces a choice between two bad options: a semver-major package release for every pattern tweak, or
behaviour changing under a version a consumer had pinned.

The rule set is now versioned on its own terms — a semver string with an explicit bump policy
(major for a renamed or removed rule id, minor for an added rule, patch for a tightened pattern or
a corrected citation). That still depends on someone remembering to bump it, so it is paired with
`rulesDigest()`: SHA-256 over a canonical `id|gate|severity` projection of the registry. The
projection is the point — prose can be corrected without moving the digest, because no finding
changed, while a severity change must move it.

The block appears in every machine-readable report: the orchestrator's `--json`, the security gate's
`--json`, every SARIF document at `tool.driver.properties`, and `orthotect explain --json`. The Node
DOM gate computes the same digest from the same source file, which is what makes the field
trustworthy rather than decorative — a digest two languages compute differently means nothing.

---

## 10. Closing Assessment

The architecture is sound and the security gate is unusually rigorous. The failure mode this review found is consistent and specific: **the gates were written to check other people's code, and were never turned on themselves.** Every critical defect — a bypassable flag, a path-based trust shortcut, an unenforced config key — is the kind of thing that a self-audit would have surfaced on day one.

Fixing that one habit (item 3 above) is worth more than any individual feature on this roadmap. A tool whose entire premise is "evidence before assertions" should be the first thing it verifies.
